# Pairing hosted on the creator’s phone

## Scope

The user chose a temporary server on the creator’s phone, accepting public-address
and port-forwarding requirements. No public signaling service is added. This feature
is in `0.0.3-preview`; older APKs do not understand phone-hosted invitations.

The phone shares a short invitation containing its numeric IP, TCP port, an ephemeral
TLS certificate pin and a single-use random token. The friend connects explicitly,
receives the offer and returns the answer automatically over TLS. Text and files
continue over WebRTC. Both people must still verify their persistent fingerprints.

## Configure and connect across the internet

1. Creator: open **Pair / verify → Connection settings**. Keep **Host pairing on this
   phone** enabled. The detected address comes from the active Android network;
   no public-IP lookup service is contacted. Prefer a reachable global IPv6 address.
2. If using IPv4 behind a router, put the router’s **public IPv4 address** in the
   creator address field. Forward the selected TCP port (default **44333**) on the
   router to that same port on the phone’s current private IP. Reserve the phone’s
   LAN address if necessary. Only do this on a router/network you administer.
3. Allow that inbound TCP port in applicable firewalls. A global IPv6 address also
   requires an inbound firewall allowance and IPv6 reachability from the other phone.
   Detection alone is not a reachability test. No UPnP/PCP or automatic router changes
   are performed. Public and local ports must match in this preview.
4. Configure STUN/TURN for the subsequent WebRTC connection as needed. TURN does not
   expose the pairing TCP listener. Mobile CGNAT, double NAT without forwarding at
   each layer, or a restrictive ISP can prevent hosting entirely.
5. Tap **Start chat → Share invitation**. Keep the creator’s app open. Friend: open
   the link in MicroMiniChat, or use **Join chat → Paste & connect**. A shared/opened
   link is prefilled for review; tap **Connect with pasted text** to initiate access.
6. No reply needs to be shared manually. Once connected, compare the full persistent
   fingerprints independently, confirm on both phones and return to chat.

Custom-scheme links may not be clickable in every messenger, and another installed
app can register the same scheme. Copy/paste into MicroMiniChat is supported. No
verified HTTPS App Link/domain ownership is claimed. Invitations grant access to
sensitive network details; exchange them only through a trusted channel.

## Security and resource boundaries

The listener uses platform TLS 1.2/1.3 with a fresh ECDSA certificate generated by the
existing WebRTC cryptographic implementation. The joiner requires its exact SHA-256
certificate pin from the invitation and checks validity; there is no trust-all manager,
plaintext fallback or shared persistent TLS private key. The ephemeral certificate,
key and random 256-bit bearer token stay in memory. TLS protects signaling only;
no additional application-content cipher or custom cryptographic handshake is added.
A stolen/replaced invitation can admit an attacker or deny pairing. Independent
persistent DTLS fingerprint verification remains mandatory before sending content.

One authorized connection can retrieve the offer and submit one session-matching
answer. The socket framing is versioned and bounded; malformed/oversized data is
rejected. Authentication/handshake has a five-second absolute limit; an authorized
exchange has a sixty-second limit; the listener expires after ten minutes. At most
32 attempted connections are handled; hostile traffic can exhaust the invitation.
A shared pool caps pairing I/O workers at four with no waiting task queue. TLS
network work never runs on the UI thread. All sockets/timers close on cancellation,
network change, process shutdown or background-grace expiry. Successful exchange
also closes the listener. No signaling, token, key or network-address logs are written.

The app has no foreground service or terminated-app listener. Short sharing switches
retain only the existing best-effort two-minute grace. Starting again invalidates the
old invitation. Disable phone hosting in Connection settings for the manual two-payload
fallback when the creator cannot accept incoming TCP connections.

## Evidence and outstanding tests

Emulator loopback tests and a signed two-app-UID UI smoke passed. The tests cover
pinned TLS, bad pins/tokens, incomplete authentication,
frame bounds, wrong-session answers, cancellation and full native-session pairing
followed by durable message acknowledgement. These do not prove internet reachability.
Real public-IPv4 forwarding, IPv6 between separate networks, mobile CGNAT failure,
OEM/background behavior and real two-phone TLS interoperability remain untested.
